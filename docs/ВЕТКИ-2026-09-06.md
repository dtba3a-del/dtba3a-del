**Вопрос автора:** «я не знаю, там 4 ветки кроме `main`; нужно сверить, что
там, или оставить. Если они не универсальны, лучше в папках сделать вложения
с особенностями? Без анализа лекарства нет?»

Последнее — верно поставлено, и потому сверка сделана прежде предложений.
Результат её таков, что предложенное лекарство не понадобилось: **особенностей
в ветках нет, различать нечего.**

## 1. Что в ветках на самом деле

| ветка | своих коммитов сверх `main` | что несёт своего |
|---|---|---|
| `claude/chatman-to-private` | **0** | ничего: указывает на `608c419`, целиком лежащий в `main` |
| `claude/chatman-tool-upload` | **0** | ничего: тот же `608c419` |
| `claude/restore-chatman` | 1 (`f066d0a`) | **ничего:** её `chatman.py` совпадает с `main` побайтно, `sha256` `ac1a5531…` у обоих |
| `au/chatman-2.1-known-subagents` | 1 (`e9b43aa`) | `chatman` 2.1 — команда `known` и выгрузка записей подагентов |

Про `claude/restore-chatman` подробнее, потому что её единственный коммит
выглядит содержательным, а содержательным не является. Работа из неё уже в
`main`: она пришла туда через PR #3 коммитом `8d24176` «Восстановлен chatman
и его правила из коммита `ab26040`». Оставшаяся ветка — снимок того же
состояния до слияния. Различие «ветка против `main`» состоит **только из
минусов**: в ней нет `CLAUDE.md`, `NOTICE.md`, `.mailmap` и
`.github/FUNDING.yml`, которые `main` получил позже. То есть она не другая,
а **отставшая**.

Разница в счёте «своих файлов» у первых трёх строк (7, 7, 4) обманчива и
потому названа отдельно: это файлы, которых в ветке **нет**, а не файлы,
которые она добавляет. Считать их содержимым ветки — та же ошибка, что
принять пустоту за находку.

## 2. Почему «папки с особенностями» заводить не нужно

Механизм, который автор предложил, **в инструменте уже есть и работает с
самого начала**. `chatman` — один файл без вариантов, а всё особенное для
проекта лежит в его собственной папке `.chatman/`, заводимой командой
`chatman init`:

| файл | что в нём |
|---|---|
| `.chatman/rules.md` | канон **этого** проекта; печатается `chatman rules` следом за общей частью |
| `.chatman/config.json` | имя проекта и его настройки |
| `.chatman/README.md` | указатель на инструмент — чтобы проект знал о нём явно, не держа копии внутри себя |

Отсюда и правило, ради которого это здесь записано: **особенность проекта
живёт в `.chatman/` проекта, а не в ветке инструмента.** Ветка для
особенности — это копия инструмента, которую придётся править дважды; папка
— это данные, которые инструмент читает. Первые три ветки как раз и
показывают, во что превращается копия: она отстаёт молча.

## 3. Решение автора и что сделано

**Распоряжение, 2026-09-06:** «`chatman-2.1-known-subagents` необходимо дать
общее правило в `main`. Остальное удалить. Таким образом `main` update.
`main` единственный бранч.»

**Сделано.** Работа ветки `au/chatman-2.1-known-subagents` в `main`
перемоткой, без узла слияния: `8213ac7 → 961e552`. Туда же легло общее
правило — раздел «Инструмент один, ветка одна: `main`» в
[`CLAUDE.md`](../CLAUDE.md), то есть оно подхватывается всяким чатом во
всяком репозитории профиля, а не остаётся разбором одного случая.

**Не сделано, и это отказ среды, а не решение исполнителя.** Удалить ветки
не удалось: `git push origin --delete` отвечает `HTTP 403`, приложению
GitHub, от имени которого работает инструмент, удаление ссылок не
разрешено. Тем же кодом отвечает и создание PR в этом репозитории.

Удалить их может автор — в веб-интерфейсе (`Branches` → корзина) либо
локально:

```bash
git push origin --delete claude/chatman-to-private
git push origin --delete claude/chatman-tool-upload
git push origin --delete claude/restore-chatman
git push origin --delete au/chatman-2.1-known-subagents
```

**Терять при этом нечего, и это проверено, а не предположено.** Первые две
ветки и `au/…` целиком содержатся в `main`. Единственный коммит
`claude/restore-chatman` (`f066d0a`) в `main` формально не входит, но его
содержимое там есть: `chatman.py` этой ветки совпадает побайтно с тем, что
лежал в `main` до обновления (`sha256` `ac1a5531…`, коммит `8d24176`,
PR #3), и остаётся доступен в истории `main`. Проверка воспроизводима:

```bash
git merge-base --is-ancestor origin/<ветка> origin/main && echo "целиком в main"
git show 8d24176:chatman/chatman.py                       | sha256sum
git show origin/claude/restore-chatman:chatman/chatman.py | sha256sum
```
